# 应用组合与 workspace 边界

`apps/api/src/app.ts` 负责跨切面 HTTP policy 和功能模块组合；`packages/todos`、`packages/system` 等包只接收宿主 app 与显式依赖。

## 依赖方向

```text
Web
├── System/Todos RPC clients ─→ 各自的 Hono 子路由类型
└── Auth Client ──────────────→ Better Auth endpoint

API（唯一组合根）
├── Auth Server ─→ Database
├── Todos ───────→ Database
├── System ──────→ 注入的数据库探针与失败回调
└── Logging + Database
```

依赖只从应用层指向能力包和基础设施包。Database 与 Logging 不反向依赖业务；Web 不导入 Auth Server、Database 或 Drizzle。

## 标准组合流程

1. 由统一 migrator 进程使用 `DATABASE_MIGRATOR_URL` 依次执行 Drizzle 与 BullMQ migration；BullMQ schema 权限固定授予 `app_runtime`。
2. 一次性 `admin-provision` 进程使用 runtime 连接创建或提升平台管理员，现有密码不会被覆盖。
3. API 和 Worker 使用 `DATABASE_RUNTIME_URL`；它们不持有 migrator 凭据或管理员初始密码。
4. 创建 Todo Service 和健康检查依赖，在 API 宿主挂载认证与平台管理路由。
5. 在组合根声明业务权限，将授权 middleware 注入 Todos 和 Jobs 管理入口。
6. 复杂模块内部用 `createHandlers()` 组合描述、校验、授权和 handler，再由 `setupXxxApp()` 使用 `app.route()` 挂载相对路径子应用。
7. 使用每个 setup 函数的返回值继续组合，保留 Hono 的精确 `AppType`。
8. System、Todos 等模块导出各自的 Hono 子路由类型；Web 按需创建独立 RPC client，并使用 Auth Client 访问认证端点，不复制 API schema。

## 边界原则

- Auth 负责身份、成员关系和权限，不实现业务查询。
- Service 负责用例和租户事务，Repository 负责显式租户条件。
- PostgreSQL RLS 是最后防线，不替代应用层授权或 Repository 条件。
- API 是唯一组合根；不使用通用模块注册器，也不让功能包创建第二个宿主 Hono app。
